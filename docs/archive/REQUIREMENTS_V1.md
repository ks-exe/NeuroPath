# Requirements Document

## Introduction

NEUROPATH is an AI engineering company platform hosted on AWS. Tagline: "Engineering Intelligence. Enabling Growth." The platform has a public marketing website, a customer platform, two Labs (Data Engineering Playground and AI Solution Architect), an internal workflow engine (ENGINE), a multi-agent business automation system (OPS), and an administration area for the Founder.

Delivery is organized in seven sequential phases. Each phase ends with a working application, and work on a phase starts only after the previous phase has been reviewed.

| Phase | Name | Scope |
|---|---|---|
| 0 | Foundation | Monorepo, tooling, database baseline, infrastructure baseline, documentation skeleton |
| 1 | Public website | Brand identity, all public pages, contact and consultation form, SEO |
| 2 | Auth and customer dashboard | Cognito auth, roles, tenancy, dashboard, projects, notifications, admin basics |
| 3 | Data Engineering Playground | Upload, profiling, AI recommendations, pipelines, execution, outputs, ML preparation |
| 4 | AI Solution Architect | Intake, analysis, classification, architecture, proposal, consultation request |
| 5 | NEUROPATH OPS | Multi-agent system, approvals, ops dashboard, full admin console |
| 6 | Production readiness | Hardening, security review, backup, monitoring, load and recovery testing |

Priority order: public website, customer platform, Data Playground, AI Solution Architect, multi-agent OPS, production hardening.

## Glossary

- **Platform**: The complete NEUROPATH system comprising Web_App, API, Data_Engine, Agent_Runtime, and Infrastructure.
- **Web_App**: The Next.js, React, TypeScript, Tailwind, and shadcn/ui frontend in `apps/web`.
- **API**: The FastAPI backend in `apps/api`, exposed under the `/api/v1` path prefix.
- **Data_Engine**: The Python package in `data_engine/` that performs profiling, validation, transformation, feature engineering, and reporting.
- **Agent_Runtime**: The Strands Agents and Amazon Bedrock based runtime in `agents/` that hosts OPS agents and Lab AI components.
- **ENGINE**: The internal workflow and pipeline execution component that runs jobs and records logs.
- **OPS**: The multi-agent business automation module reachable at `/admin/ops`.
- **Infrastructure**: AWS resources defined as code in `infrastructure/` using CDK or Terraform.
- **Auth_Service**: Amazon Cognito user pools and the API components that verify Cognito tokens.
- **Guest**: An unauthenticated visitor.
- **Registered_Customer**: An authenticated, email-verified user on the base tier.
- **Premium_Customer**: An authenticated user with elevated usage limits.
- **Administrator**: An authenticated NEUROPATH staff user with administrative permissions.
- **Founder**: The highest-privilege role, which includes all Administrator permissions plus approval authority over OPS actions.
- **Internal_Agent**: A non-human principal that may call only the API tasks explicitly authorized for that agent.
- **Organization**: A tenant that owns users, datasets, pipelines, projects, and proposals.
- **Dataset**: A user-uploaded file in CSV, XLSX, or JSON format and its metadata.
- **Profile**: The computed statistical and quality description of a Dataset.
- **Pipeline**: An ordered list of allowlisted Operations applied to a Dataset.
- **Operation**: A deterministic, allowlisted, parameterized data transformation implemented in the Data_Engine.
- **Recommendation**: An AI-suggested Operation list that is a proposal only and is not executed until a user approves it.
- **Execution**: One run of a Pipeline, with per-Operation status, timing, counts, warnings, errors, and logs.
- **Job**: An asynchronous unit of long-running work identified by a job ID.
- **Solution_Architect**: The AI Solution Architect Lab that converts a problem description into a preliminary solution.
- **Proposal**: A downloadable document generated by the Solution_Architect.
- **Project**: A customer engagement record with a status lifecycle.
- **Lead**: A record of a prospective customer created from inquiries or Lead Research.
- **Agent_Task**: A unit of work assigned to an OPS agent.
- **Approval_Request**: A recorded request for a Founder decision on a sensitive action.
- **Sensitive_Action**: Any of: sending emails, publishing social content, contacting prospects, making purchases, spending on advertising, modifying production infrastructure, deleting customer data, sharing confidential information, issuing commercial quotations.
- **Audit_Log**: An append-only record of who did what, to which resource, and when.
- **Presigned_URL**: A short-lived Amazon S3 URL scoped to a single object and operation.
- **Feature_Flag**: A runtime switch managed in the admin console that enables or disables a capability.
- **Design_System**: The "Editorial Brutalism x Engineering Journal" visual language defined in Requirement 4.
- **Real_Result**: A value derived from actual execution of code or a persisted record, never from placeholder or invented data.

## Requirements

## Phase 0: Foundation

### Requirement 1: Monorepo Structure

**User Story:** As a developer, I want a documented monorepo layout, so that every module has a predictable home and can be built and tested independently.

#### Acceptance Criteria

1. THE Platform repository SHALL contain the top-level directories `apps/web`, `apps/api`, `agents`, `data_engine`, `packages`, `infrastructure`, `docs`, and `scripts`.
2. THE `apps/api` directory SHALL contain the subdirectories `api`, `core`, `models`, `schemas`, `services`, `repositories`, `workers`, and `tests`.
3. THE `agents` directory SHALL contain one subdirectory for each OPS agent: orchestrator, business_intelligence, marketing, content, lead_research, outreach, engineering, data, and quality_security.
4. THE `data_engine` directory SHALL contain the subdirectories `profiling`, `validation`, `transformations`, `feature_engineering`, and `reporting`.
5. IF the implemented structure deviates from the layout in this requirement, THEN THE Platform SHALL document each deviation and its rationale in `docs/ARCHITECTURE.md`.

### Requirement 2: Technology Stack and Architecture Decisions

**User Story:** As a developer, I want a fixed, minimal technology stack with recorded decisions, so that the MVP stays modular and avoids unneeded services.

#### Acceptance Criteria

1. THE Web_App SHALL be implemented with Next.js, React, TypeScript, Tailwind CSS, shadcn/ui, and React Flow.
2. THE API SHALL be implemented with Python, FastAPI, Pydantic, SQLAlchemy, and Alembic.
3. THE Platform SHALL use PostgreSQL on Amazon RDS for relational data and Amazon S3 for file storage.
4. THE Agent_Runtime SHALL use Amazon Bedrock models and Strands Agents with structured outputs.
5. THE Infrastructure SHALL use AWS Step Functions, Amazon SQS, Amazon EventBridge, AWS Lambda, Amazon ECS on Fargate, Amazon Cognito, Amazon CloudWatch, and AWS Secrets Manager only where a requirement in this document needs them.
6. THE Infrastructure SHALL be defined as code in either CDK or Terraform, selected once and recorded in `docs/ARCHITECTURE.md`.
7. WHEN an architectural decision is made, THE Platform SHALL record the decision, alternatives considered, and rationale in `docs/ARCHITECTURE.md`.
8. THE Web_App SHALL NOT call privileged AWS services and SHALL NOT contain secrets or AWS credentials.

### Requirement 3: Local Development and External Service Fallbacks

**User Story:** As a developer, I want to run the Platform locally without every AWS service available, so that development continues when a credential or service is unavailable.

#### Acceptance Criteria

1. THE Platform SHALL provide a documented local development setup in `docs/DEVELOPMENT.md` and `docs/ENVIRONMENT.md` that lists every environment variable, its purpose, and whether it is a secret.
2. THE Platform SHALL load secrets from environment variables locally and from AWS Secrets Manager in deployed environments.
3. IF a required credential or external service is unavailable, THEN THE Platform SHALL provide a documented integration interface together with a safe local implementation.
4. IF a local implementation substitutes for an external service, THEN THE Platform SHALL identify the substitution in `docs/IMPLEMENTATION_STATUS.md` and SHALL return no fabricated success result to callers.
5. THE Platform SHALL keep each external integration (Bedrock, S3, Cognito, malware scanner, email) behind an interface so that the implementation is replaceable without changing callers.
6. THE Infrastructure SHALL NOT create billable AWS resources until the Founder has explicitly authorized the deployment in writing.
7. THE Platform repository SHALL contain no hardcoded secrets, and a secret scanning check SHALL run in the continuous integration pipeline.

### Requirement 4: Design System

**User Story:** As a visitor, I want a distinctive, consistent interface, so that NEUROPATH is recognizable and credible.

#### Acceptance Criteria

1. THE Web_App SHALL implement the Design_System "Editorial Brutalism x Engineering Journal" through shared design tokens.
2. THE Web_App SHALL use the colors #762B3B (primary), #F4F0E9 (background), #171515 (dark), #D9D0C6 (secondary), and #A76C58 (accent).
3. THE Web_App SHALL use Playfair Display for headings, Manrope for body text, and IBM Plex Mono for code, labels, and technical text.
4. THE Web_App SHALL use no purple gradients, no glassmorphism, no robot imagery, and border radii no larger than 4 px on cards.
5. THE Web_App SHALL limit motion to subtle transitions of 300 ms or less.
6. WHILE the user's operating system reports a reduced-motion preference, THE Web_App SHALL disable non-essential animation.
7. THE Web_App SHALL render without horizontal scrolling at viewport widths of 360 px, 768 px, 1280 px, and 1920 px.

### Requirement 5: Documentation Set

**User Story:** As a stakeholder, I want current documentation after every phase, so that status and decisions are always visible.

#### Acceptance Criteria

1. THE Platform repository SHALL contain `README.md` and, in `docs/`, PRD, ARCHITECTURE, DATABASE, API, SECURITY, DEVELOPMENT, DEPLOYMENT, TESTING, ENVIRONMENT, CHANGELOG, and IMPLEMENTATION_STATUS documents.
2. THE IMPLEMENTATION_STATUS document SHALL list completed work, incomplete work, known bugs, technical debt, blockers, tests run with results, and next tasks.
3. WHEN a phase is completed, THE Platform SHALL update every affected document in the same change set as the phase deliverables.
4. THE Platform SHALL mark a feature as complete in IMPLEMENTATION_STATUS only when automated tests covering the feature exist and pass.

### Requirement 6: Database Baseline

**User Story:** As a developer, I want a migration-managed relational schema, so that data is consistent and tenant-isolated.

#### Acceptance Criteria

1. THE API SHALL define tables for users, organizations, organization_members, datasets, dataset_profiles, pipelines, pipeline_executions, projects, solution_proposals, agents, agent_tasks, approval_requests, leads, content_items, and audit_logs.
2. THE API SHALL apply every schema change through an Alembic migration.
3. THE API SHALL define foreign keys, unique constraints, and indexes for every relationship and every column used for tenant filtering or lookup.
4. THE API SHALL include an `organization_id` column on each tenant-owned table.
5. THE API SHALL exclude from each tenant-scoped repository method any query that omits an organization filter, except for methods restricted to Administrator or Founder callers.
6. WHEN a migration is applied and then reverted on an empty database, THE API SHALL leave the database schema equal to its starting state.
7. THE DATABASE document SHALL describe each table, column, and relationship.
8. THE API SHALL create the tables required by a phase in a migration delivered in that phase or an earlier phase.

### Requirement 7: Continuous Verification and Cost Control

**User Story:** As the Founder, I want automated checks and cost guardrails, so that quality and spending stay under control.

#### Acceptance Criteria

1. THE Platform SHALL provide a single documented command for each of: lint, type check, unit tests, and build for each of Web_App and API.
2. WHEN a change is pushed, THE continuous integration pipeline SHALL run lint, type check, tests, and secret scanning.
3. THE Infrastructure SHALL tag every AWS resource with project, environment, and owner tags.
4. THE Infrastructure SHALL define an AWS budget alarm for each deployed environment.
5. WHERE a new AWS service not listed in Requirement 2 is proposed, THE Platform SHALL record a justification in `docs/ARCHITECTURE.md` before the service is provisioned.

## Phase 1: Public Website

**User Story:** As a visitor, I want consistent navigation, so that I can find any section from any page.

1. THE Web_App SHALL display navigation links Home, Services, Labs, Solutions, Projects, About, Insights, and Contact on every public page.
2. THE Web_App SHALL display Sign In and Get Started actions in the header on every public page.
3. WHEN the viewport width is below 768 px, THE Web_App SHALL replace the navigation links with a menu control that opens and closes the full navigation.
4. THE Web_App SHALL highlight the navigation item for the current page and set `aria-current="page"` on it.
5. THE Web_App SHALL display a footer on every public page containing links to all navigation destinations.
6. WHILE a Guest views a public page, THE Web_App SHALL operate without requiring authentication.
7. WHERE the Auth_Service is not yet enabled in the current phase, THE Web_App SHALL show Sign In and Get Started as links to a page that states the account feature is not yet available.

### Requirement 9: Homepage

**User Story:** As a visitor, I want a homepage that explains what NEUROPATH does, so that I can decide whether to engage.

#### Acceptance Criteria

1. THE Web_App SHALL render the homepage with these sections in order: Hero, What We Do, Experience Our Engineering, Engineering Capabilities, Selected Projects, How We Work, and Final CTA.
2. THE Hero section SHALL display the tagline "Engineering Intelligence. Enabling Growth." and two calls to action labeled "Explore Our Labs" and "Discuss Your Project".
3. WHEN a visitor activates "Explore Our Labs", THE Web_App SHALL navigate to the Labs page.
4. WHEN a visitor activates "Discuss Your Project", THE Web_App SHALL navigate to the Contact page.
5. THE What We Do section SHALL present six service categories: AI/ML Engineering, Data Engineering, Cloud & DevOps, Software Engineering, Web Scraping & Data Collection, and Technical Consulting.
6. THE Experience Our Engineering section SHALL present two Labs cards: Data Engineering Playground and AI Solution Architect.
7. THE How We Work section SHALL present six numbered steps in the order Discover, Analyze, Design, Build, Validate, and Deliver.
8. THE Final CTA section SHALL display the heading "Have a problem worth engineering?" and a button labeled "Start a Conversation" that navigates to the Contact page.
9. WHILE a Lab is not yet available in the current phase, THE Web_App SHALL label the corresponding card as "Coming soon" and SHALL NOT link it to a non-functional page.

### Requirement 10: Truthful Content

**User Story:** As the Founder, I want the website to contain only true claims, so that NEUROPATH's credibility is protected.

#### Acceptance Criteria

1. THE Selected Projects section SHALL display only projects that exist in a content source maintained by NEUROPATH and verified by the Founder.
2. THE Web_App SHALL NOT display invented customers, invented results, invented metrics, or invented testimonials.
3. IF no verified project exists, THEN THE Selected Projects section SHALL display a statement that project case studies are being prepared, without placeholder project entries.

5. THE Web_App SHALL omit any project entry whose verification flag is not set to verified.

### Requirement 11: Services Pages

**User Story:** As a prospective customer, I want clear service descriptions, so that I can match my need to a NEUROPATH capability.

#### Acceptance Criteria

1. THE Web_App SHALL provide a Services page that lists the six service categories, each linking to a detail section or page.
2. THE detail content for each service SHALL describe typical engagements, deliverables, and technologies, and SHALL contain no unverifiable performance claims.
3. THE Web Scraping & Data Collection service content SHALL state that engagements respect applicable laws, website terms of service, access controls, and privacy requirements.
4. THE Web_App SHALL display on each service detail a call to action that navigates to the Contact page with the service pre-selected.

### Requirement 12: Additional Public Pages

**User Story:** As a visitor, I want pages for Labs, Solutions, Projects, About, and Insights, so that I can learn about the company and its work.

#### Acceptance Criteria

1. THE Web_App SHALL provide public pages for Labs, Solutions, Projects, About, and Insights.
2. THE Labs page SHALL describe Data Engineering Playground, AI Solution Architect, and Engineering Service Request, and SHALL show the availability status of each.
3. THE Projects page SHALL apply the truthful content rules in Requirement 10.
4. THE Insights page SHALL list only published articles from a structured content source, and IF no article is published, THEN THE Insights page SHALL state that articles are forthcoming.

### Requirement 13: Contact and Consultation Form

**User Story:** As a prospective customer, I want to send an inquiry, so that NEUROPATH can contact me about my project.

#### Acceptance Criteria

1. THE Contact page SHALL provide a form with fields for name, email, company, service of interest, message, and a consent checkbox for contact and data processing.
2. WHEN a visitor submits the form with name, a syntactically valid email, a message of at least 20 characters, and consent given, THE API SHALL store a Lead record and return a success response.
3. IF a required field is empty, an email is syntactically invalid, or consent is not given, THEN THE Web_App SHALL show a field-specific error message next to the offending field and SHALL NOT submit the form.
4. IF the API rejects a submission, THEN THE Web_App SHALL display the error and preserve the entered values.
5. WHEN a submission succeeds, THE Web_App SHALL display a confirmation message and clear the form.
6. THE API SHALL limit anonymous form submissions to 5 per client IP address per 10 minutes and SHALL return a rate-limit error beyond that limit.
7. THE API SHALL include a honeypot field check and reject submissions that fill it.
8. THE API SHALL sanitize submitted text before storage and rendering.
9. THE API SHALL write an Audit_Log entry for each stored Lead.
10. THE Platform SHALL notify NEUROPATH of each new Lead by a method that does not send email to the submitter without Founder approval.
11. WHILE the form request is pending, THE Web_App SHALL disable the submit control and show a loading state.

### Requirement 14: SEO, Performance, and Accessibility of the Public Website

**User Story:** As the Founder, I want the website to be discoverable and accessible, so that it reaches more visitors.

#### Acceptance Criteria

1. THE Web_App SHALL set a unique title, meta description, canonical URL, and Open Graph metadata on every public page.
2. THE Web_App SHALL generate a sitemap and a robots file.
3. THE Web_App SHALL render exactly one h1 element per public page and a logical heading hierarchy.
4. THE Web_App SHALL provide text alternatives for every meaningful image.
5. THE Web_App SHALL meet WCAG 2.2 level AA contrast for text and interactive controls, including focus indicators.
6. THE Web_App SHALL allow every interactive element to be operated with the keyboard alone.
7. THE Web_App SHALL associate every form control with a visible label.
8. WHEN an error or status message appears, THE Web_App SHALL announce the message to screen readers through an appropriate live region or focus move.
9. THE public homepage SHALL achieve Lighthouse scores of at least 90 for Performance, Accessibility, Best Practices, and SEO on a mobile profile in a production build.
10. THE Web_App SHALL load only the fonts and scripts required by each page.

## Phase 2: Authentication and Customer Dashboard

### Requirement 15: Registration, Sign-In, and Account Recovery

**User Story:** As a customer, I want secure account management, so that I can access my data safely.

#### Acceptance Criteria

1. THE Auth_Service SHALL perform authentication through Amazon Cognito, and THE Platform SHALL NOT store or process passwords outside Cognito.
2. WHEN a visitor registers with a valid email and a password that meets the policy, THE Auth_Service SHALL create an unverified account and send a verification message.
3. IF an account email is not verified, THEN THE Auth_Service SHALL deny sign-in until verification is completed.
4. WHEN a user requests password recovery, THE Auth_Service SHALL send a reset code to the registered email and SHALL return the same response whether or not the email is registered.
5. THE Auth_Service SHALL enforce a password policy of at least 12 characters.
6. THE API SHALL provide endpoints `/api/v1/auth/register`, `/api/v1/auth/login`, `/api/v1/auth/logout`, and `/api/v1/auth/me`.
7. WHEN a user signs out, THE API SHALL invalidate the session and the Web_App SHALL clear client session state.
8. WHEN a user registers, THE API SHALL create a user record and a default Organization with the user as owner member.
9. IF five consecutive failed sign-in attempts occur for one account, THEN THE Auth_Service SHALL apply a temporary lockout.
10. THE Web_App SHALL store session tokens only in HTTP-only, secure, same-site cookies.

### Requirement 16: Roles and Authorization

**User Story:** As the Founder, I want strict role-based access, so that users and agents only do what they are permitted to do.

#### Acceptance Criteria

1. THE API SHALL support the roles Guest, Registered_Customer, Premium_Customer, Administrator, Founder, and Internal_Agent.
2. THE API SHALL treat Founder as having every permission held by Administrator and every permission held by Premium_Customer.
3. THE API SHALL check authentication and authorization on every endpoint other than public endpoints, and SHALL deny by default.
4. IF a request lacks valid authentication, THEN THE API SHALL return HTTP 401 with a structured error.
5. IF an authenticated principal lacks permission for the endpoint, THEN THE API SHALL return HTTP 403 with a structured error.
6. THE API SHALL grant an Internal_Agent access only to endpoints listed in that agent's explicit permission set.
7. THE API SHALL NOT grant any Internal_Agent the Administrator or Founder role or unrestricted administrative access.
8. THE Web_App SHALL hide controls the current user may not use, and THE API SHALL enforce the same restrictions independently.
9. THE API SHALL write an Audit_Log entry for each role change.

### Requirement 17: Tenant Isolation

**User Story:** As a customer, I want my data visible only to my organization, so that confidential information remains private.

#### Acceptance Criteria

1. THE API SHALL scope every query for tenant-owned data to the authenticated principal's Organization.
2. IF a user requests a resource that belongs to a different Organization, THEN THE API SHALL return HTTP 404 and SHALL NOT disclose that the resource exists.
3. THE API SHALL store customer objects in S3 under keys prefixed by organization identifier, and SHALL verify the prefix before issuing any Presigned_URL.
4. THE API SHALL provide endpoints for current user and Organization data at `/api/v1/users/me` and `/api/v1/organizations`.
5. FOR ALL pairs of distinct Organizations A and B, no API response to a user of A SHALL contain any record owned by B (isolation property).

### Requirement 18: Customer Dashboard Overview and Notifications

**User Story:** As a customer, I want a dashboard, so that I can see my activity and respond to events.

#### Acceptance Criteria

1. THE Web_App SHALL provide an authenticated dashboard at `/dashboard` showing counts and recent items for the user's datasets, pipelines, projects, and proposals, computed from stored records.
2. IF the user has no records of a type, THEN THE Web_App SHALL show an empty state that explains the next action.
3. WHILE dashboard data is loading, THE Web_App SHALL show a loading state, and IF loading fails, THEN THE Web_App SHALL show an error state with a retry control.
4. WHEN upload completion, profiling completion, pipeline completion, pipeline failure, solution generation, or a project status update occurs, THE Platform SHALL create an in-app notification for the owning user.
5. THE Web_App SHALL show an unread notification count and allow marking notifications as read.
6. THE Platform SHALL send an email notification only for events the user has opted into.
7. WHEN an unauthenticated user requests a `/dashboard` route, THE Web_App SHALL redirect the user to Sign In and return the user to the requested route after sign-in.

### Requirement 19: Project Management for Customers

**User Story:** As a customer, I want to submit and follow projects, so that I can track an engagement with NEUROPATH.

#### Acceptance Criteria

1. THE API SHALL provide endpoints to create, list, get, and patch Projects and to request a consultation, under `/api/v1/projects`.
2. THE Project status SHALL be one of Draft, Submitted, Under Review, Proposal Generated, Awaiting Customer Approval, Accepted, In Progress, Completed, and Cancelled.
3. THE API SHALL accept only status transitions that are defined in a documented transition table, and IF a transition is not allowed, THEN THE API SHALL return a structured error.
4. THE API SHALL allow a customer to move a Project only to Submitted, Accepted, or Cancelled from the states permitted by the transition table.
5. WHEN a Project status changes, THE API SHALL record the change in the Audit_Log and create a notification for the owning user.
6. THE Web_App SHALL display each Project with its status, proposals, shared documents, and communication thread.
7. THE API SHALL expose to a customer only the shared documents and messages marked as customer-visible, and SHALL withhold internal notes.
8. WHEN a customer submits an inquiry from the dashboard, THE API SHALL create a Project in Submitted status and a linked Lead record.

### Requirement 20: Basic Administration in Phase 2

**User Story:** As the Founder, I want basic administration early, so that I can manage customers and inquiries as soon as they arrive.

#### Acceptance Criteria

1. THE Web_App SHALL provide an admin area at `/admin` accessible only to Administrator and Founder roles.
2. THE admin area SHALL show counts of customers, registrations, inquiries, and active Projects computed from stored records.
3. THE admin area SHALL list customers and allow an Administrator to suspend and reinstate a customer account.
4. IF an account is suspended, THEN THE API SHALL deny all requests from that account's users with a structured error.
5. THE admin area SHALL allow an Administrator to assign a Project, change its status, add internal notes, and attach deliverables.
6. THE API SHALL write an Audit_Log entry for every administrative action.

### Requirement 21: Rate Limiting, Validation, and Structured Errors

**User Story:** As a developer, I want uniform API behavior, so that clients handle failures predictably.

#### Acceptance Criteria

1. THE API SHALL validate every request body, query parameter, and path parameter with Pydantic schemas.
2. IF validation fails, THEN THE API SHALL return HTTP 422 with an error body that contains a machine-readable code, a human-readable message, and the list of offending fields.
3. THE API SHALL return every error in one documented structured error format that includes a request identifier.
4. THE API SHALL apply per-principal and per-IP rate limits, and IF a limit is exceeded, THEN THE API SHALL return HTTP 429 with a retry-after value.
5. WHEN an endpoint starts long-running work, THE API SHALL return HTTP 202 with a job ID, and THE API SHALL provide a way to poll the job status.
6. THE API SHALL expose an OpenAPI description that matches `docs/API.md`.

### Requirement 22: Pricing and Monetization Posture

**User Story:** As the Founder, I want services-first monetization with future tiers, so that billing starts only when it is safe.

#### Acceptance Criteria

1. THE Platform SHALL operate in Phase 1 through Phase 6 as a services-first offering with no payment processing.
2. THE Platform SHALL define future tiers named Free, Starter, Professional, and Enterprise in `docs/PRD.md`, with usage limits per tier held in configuration.
3. THE Platform SHALL record usage per Organization for uploads, storage, jobs, and AI calls.
4. THE Platform SHALL record estimated cost per Job and per AI call.
5. THE Platform SHALL NOT enable billing until usage limits and cost tracking pass their tests and the Founder has approved enabling billing.
6. IF an Organization exceeds a configured usage limit, THEN THE API SHALL reject the further usage request with a structured error that names the exceeded limit.

## Phase 3: Data Engineering Playground

### Requirement 23: Dataset Upload

**User Story:** As a customer, I want to upload a data file safely, so that I can analyze and prepare it.

#### Acceptance Criteria

1. THE Web_App SHALL provide the Data Playground at `/labs/data-playground`.
2. THE Data_Engine SHALL accept CSV, XLSX, and JSON files, and THE Data_Engine SHALL isolate format handling behind an interface so that Parquet and JSONL can be added later.
3. THE Platform SHALL read the maximum file size, maximum row count, and maximum processing time from configuration per role and per tier.
4. THE Web_App SHALL provide drag-and-drop and file-picker upload, with client-side validation of extension and size before upload begins.
5. THE Web_App SHALL show a progress indicator during upload and a control to cancel the upload.
6. THE Web_App SHALL require the user to confirm permission to process the file before upload begins.
7. WHEN an upload is requested, THE API SHALL return a Presigned_URL valid for no more than 10 minutes, scoped to one key under the Organization's prefix.
8. WHEN the upload finishes, THE API SHALL accept a complete-upload request and create a Dataset record only after verifying the object exists.
9. THE API SHALL validate on the server both the file extension and the real content type by inspecting file content.
10. IF a file has a disallowed extension, a content type that does not match its extension, a size above the limit, a malformed structure, or exceeds the row limit, THEN THE API SHALL reject the file, delete the stored object, and return an error that names the reason.
11. THE API SHALL scan each uploaded file for malware before processing, and IF the scan detects malware or is unavailable, THEN THE API SHALL quarantine the file and SHALL NOT process it.
12. THE API SHALL enforce size, row, and time limits for each file independently of client checks.
13. THE API SHALL provide dataset endpoints upload-url, complete-upload, list, get, delete, and profile under `/api/v1/datasets`.
14. THE Platform SHALL process uploaded files in an isolated environment with CPU, memory, and time limits and no access to other Organizations' data.

### Requirement 24: Data Profiling

**User Story:** As a customer, I want accurate profiling of my data, so that I understand its quality before changing it.

#### Acceptance Criteria

1. WHEN profiling is requested for a Dataset, THE API SHALL start a Job and return its job ID.
2. THE Data_Engine SHALL compute, from the actual file contents, row count, column count, inferred type per column, missing-value count and percentage, and duplicate-row count.
3. THE Data_Engine SHALL compute for numeric columns the mean, median, standard deviation, minimum, and maximum, and for categorical columns the unique-value count and value frequencies.
4. THE Data_Engine SHALL detect invalid values, outliers, inconsistent formats, wrong types, and leakage indicators and SHALL report for each finding the column, the count of affected rows, and the detection rule used.
5. THE Data_Engine SHALL store the resulting Profile in the dataset_profiles table.
6. THE Web_App SHALL display the Profile in an interactive dashboard with sortable column summaries, distribution charts, and a list of quality issues.
7. FOR ALL Datasets, THE Profile row count SHALL equal the number of data rows in the file (invariant).
8. FOR ALL Datasets, profiling the same file twice SHALL produce identical Profiles (idempotence).
9. IF the file cannot be parsed, THEN THE Data_Engine SHALL mark the profiling Job failed with an error message and SHALL NOT store a partial Profile.
10. THE Web_App SHALL show profiling status as queued, running, completed, or failed and announce status changes to screen readers.

### Requirement 25: AI Recommendations for Data Operations

**User Story:** As a customer, I want suggested cleaning steps, so that I can improve my data without deep expertise.

#### Acceptance Criteria

1. WHEN a Profile is complete and the user requests recommendations, THE Agent_Runtime SHALL return a list of Recommendations as structured output validated against a Pydantic schema.
2. THE Agent_Runtime SHALL send to the model only the Profile statistics and a bounded sample of values, and SHALL exclude raw rows beyond that sample.
3. THE Web_App SHALL disclose to the user, before the first request, which data is sent to the AI provider.
4. IF the model output fails schema validation, THEN THE Agent_Runtime SHALL retry at most 2 times and then return a structured error with no Recommendation.
5. THE API SHALL accept a Recommendation only if it names an Operation in the allowlist and its parameters pass that Operation's parameter schema.
6. IF a Recommendation names an Operation not in the allowlist or has invalid parameters, THEN THE API SHALL discard the Recommendation and record the discard reason.
7. THE Platform SHALL NOT execute any code generated by a model.
8. THE Web_App SHALL display for each Recommendation the Operation, parameters, affected columns, and the reason, and SHALL label the Recommendation as AI-generated.
9. THE Agent_Runtime SHALL treat Dataset contents as untrusted input, and an instruction embedded in Dataset values SHALL NOT alter Agent_Runtime behavior.

### Requirement 26: Pipeline Builder

**User Story:** As a customer, I want a reviewable pipeline, so that I control exactly what happens to my data.

#### Acceptance Criteria

1. THE API SHALL provide pipeline endpoints create, list, get, patch, validate, and execute under `/api/v1/pipelines`, and an executions listing at `/api/v1/pipelines/{id}/executions`.
2. THE Web_App SHALL display a Pipeline as a visual graph of Operations that the user can inspect.
3. THE Web_App SHALL let the user enable or disable each Operation, edit its parameters, and preview the effect on a bounded sample before execution.
4. THE Data_Engine SHALL compute each preview from the actual sample using the same Operation code used in execution.
5. WHEN the user changes a Pipeline, THE API SHALL store a new version and keep prior versions.
6. WHEN validation is requested, THE API SHALL check that each Operation is allowlisted, parameters are valid, referenced columns exist, and Operation order is compatible, and SHALL return each problem with its Operation identifier.
7. THE API SHALL require a recorded user approval of the current Pipeline version before it can be executed.
8. WHEN a Pipeline is modified after approval, THE API SHALL clear the approval.
9. WHERE an Operation is destructive, THE Web_App SHALL require explicit confirmation naming the Operation and the affected columns or rows count before approval.
10. THE Data_Engine SHALL implement an allowlist containing at least: remove duplicates, drop columns, drop rows by condition, fill missing values, convert types, standardize formats, trim and normalize text, clip or remove outliers, rename columns, and filter rows.
11. THE Data_Engine SHALL NOT modify the original uploaded file.

### Requirement 27: Pipeline Execution and Logs

**User Story:** As a customer, I want a transparent execution record, so that I can trust and audit the results.

#### Acceptance Criteria

1. WHEN execution of an approved Pipeline is requested, THE API SHALL start a Job and return its job ID.
2. THE Data_Engine SHALL execute Operations in order using Pandas, Polars, PyArrow, and scikit-learn implementations that are deterministic for identical inputs and parameters.
3. THE Data_Engine SHALL record per Operation the status, start time, end time, records processed, records affected, warnings, errors, and log lines.
4. IF an Operation fails, THEN THE Data_Engine SHALL stop the Execution, mark it failed, preserve the logs, and create no output marked as completed.
5. WHEN an Execution fails, THE Platform SHALL create a notification for the owner.
6. THE Web_App SHALL show live Execution status and let the user view logs.
7. THE Platform SHALL exclude raw data values and secrets from logs, recording only counts, column names, and Operation names.
8. THE Platform SHALL enforce the configured time and resource limits and terminate an Execution that exceeds them with status failed and a reason.
9. WHEN the same Job is delivered more than once by the queue, THE ENGINE SHALL process the Job once and ignore duplicate deliveries.
10. THE ENGINE SHALL retry a transient infrastructure failure up to 3 times with backoff before marking the Job failed.

### Requirement 28: Outputs, Downloads, and Completion Dashboard

**User Story:** As a customer, I want the processed data and a report, so that I can use and share my results.

#### Acceptance Criteria

1. WHEN an Execution completes, THE Data_Engine SHALL produce a cleaned dataset, a quality report, a transformation summary, a pipeline configuration file, and metadata.
2. WHERE ML preparation is configured, THE Data_Engine SHALL also produce an ML-ready dataset.
3. THE API SHALL provide download of datasets as CSV, Parquet, JSON, and XLSX through Presigned_URLs valid for no more than 10 minutes and issued only to members of the owning Organization.
4. THE Web_App SHALL display a completion dashboard whose metrics (rows before and after, columns before and after, missing values before and after, duplicates removed, per-Operation counts, duration) derive only from the recorded Execution.
5. FOR ALL Executions, the row count in the quality report SHALL equal the sum of the row counts reported by the recorded Operations applied to the input row count (output-integrity property).
6. FOR ALL downloadable formats of one output, THE Data_Engine SHALL produce files that represent the same rows and columns, within the limits of the format.
7. WHEN a CSV output is written and then read back, THE Data_Engine SHALL produce a dataset equal to the written dataset (round-trip property).
8. THE Web_App SHALL provide pages `/dashboard/datasets`, `/dashboard/datasets/[datasetId]`, `/dashboard/pipelines`, `/dashboard/pipelines/[pipelineId]`, and `/dashboard/reports/[reportId]`.
9. THE Web_App SHALL display no metric that is not backed by a stored record.

### Requirement 29: Machine Learning Preparation

**User Story:** As a customer, I want ML-oriented preparation without leakage, so that my train and test results are valid.

#### Acceptance Criteria

1. THE Data_Engine SHALL provide Operations for categorical encoding, feature scaling, missing-value treatment, feature selection, feature engineering, and train, validation, and test splitting.
2. THE Web_App SHALL require the user to choose a target column before enabling any ML preparation Operation.
3. THE Data_Engine SHALL perform the split before fitting any encoder, scaler, imputer, or selector.
4. THE Data_Engine SHALL fit each encoder, scaler, imputer, and selector on the training split only and apply the fitted transform to the validation and test splits.
5. THE Data_Engine SHALL store the fitted transform metadata with the output so that the same transforms can be reapplied.
6. IF a candidate feature is flagged as a leakage indicator relative to the target, THEN THE Web_App SHALL warn the user and require confirmation to keep the feature.
7. THE Data_Engine SHALL accept a random seed and produce the same split for the same input and seed.
8. FOR ALL splits, THE Data_Engine SHALL produce train, validation, and test sets with no shared row identifiers and a combined row count equal to the input row count.
9. THE Web_App SHALL describe the output as prepared for modeling and SHALL NOT claim that the data is ML-ready for every model or purpose.

### Requirement 30: Dataset Lifecycle, Retention, and Privacy

**User Story:** As a customer, I want control over my data, so that I can delete it and know how it is used.

#### Acceptance Criteria

1. WHEN a user deletes a Dataset, THE API SHALL remove the stored object, derived outputs, and Profile, and SHALL record the deletion in the Audit_Log.
2. THE Platform SHALL apply a configurable retention period to Datasets and outputs and delete expired items automatically.
3. THE Platform SHALL NOT use customer data to train or fine-tune any model unless the owning Organization has given explicit, recorded consent.
4. THE Platform SHALL NOT expose customer data publicly.
5. THE Web_App SHALL display the retention period for each Dataset.
6. WHEN a Dataset deletion completes, THE Web_App SHALL show a confirmation, and THE API SHALL return HTTP 404 for subsequent requests for that Dataset.

## Phase 5: NEUROPATH OPS

### Requirement 37: Agent Architecture

**User Story:** As the Founder, I want specialized agents, so that business automation is decomposed, inspectable, and safe.

#### Acceptance Criteria

1. THE Agent_Runtime SHALL implement the agents Orchestrator, Business Intelligence, Marketing, Content, Lead Research, Outreach, Engineering, Data, and Quality & Security, each with its own folder, instructions, tool list, and output schema.
2. THE Agent_Runtime SHALL give each agent a separate, scoped prompt and SHALL NOT implement multiple agents as one combined prompt.
3. THE Agent_Runtime SHALL give each agent only the tools listed for that agent and SHALL deny a call to any other tool.
4. THE Agent_Runtime SHALL validate every agent output against that agent's Pydantic schema.
5. THE Agent_Runtime SHALL provide each agent only the minimum raw customer data needed for the task, and SHALL exclude raw Dataset contents from agent inputs by default.
6. THE Agent_Runtime SHALL treat all inbound content, including customer messages and fetched web content, as untrusted and SHALL NOT let such content change an agent's instructions or tool permissions.
7. THE Content agent SHALL check each factual claim in generated content against verified project records and SHALL flag any claim lacking support.
8. THE Orchestrator SHALL route work to other agents by creating Agent_Tasks and SHALL NOT perform other agents' functions.

### Requirement 38: Task Execution and Recording

**User Story:** As the Founder, I want every agent run recorded, so that I can investigate any outcome.

#### Acceptance Criteria

1. WHEN an Agent_Task is created, THE OPS SHALL queue the task for the target agent and record the task with status queued.
2. WHEN an agent executes a task, THE OPS SHALL record the task identifier, agent identifier, input, output, status, duration, model, token counts, estimated cost, and error.
3. THE OPS SHALL redact secrets and personal data from stored inputs and outputs according to a documented redaction policy.
4. IF an agent task fails, THEN THE OPS SHALL store the error and make the task, input, and trace available to the Founder.
5. THE OPS SHALL retry transient failures up to 3 times with backoff and SHALL then mark the task failed.
6. THE OPS SHALL enforce a configurable per-task token limit and per-day cost limit and SHALL stop further tasks and notify the Founder when the daily limit is reached.
7. THE API SHALL provide admin endpoints for agents, agent-tasks, and approvals under `/api/v1/admin`.

### Requirement 39: Project Inquiry Workflow

**User Story:** As the Founder, I want inquiries processed automatically up to the point of my decision, so that I can respond quickly.

#### Acceptance Criteria

1. WHEN a project inquiry is received, THE Platform SHALL create the Project record and emit an event to the Orchestrator.
2. WHEN the Orchestrator receives the event, THE OPS SHALL run requirement analysis, then engineering solution drafting, then business intelligence classification, then quality review, in that order.
3. IF a step fails, THEN THE OPS SHALL halt the workflow, record the failing step, and notify the Founder.
4. WHEN quality review completes, THE OPS SHALL create an Approval_Request for the Founder.
5. WHILE no Founder approval exists, THE OPS SHALL keep the resulting content unshared and unavailable to the customer.
6. WHEN the Founder approves, THE OPS SHALL mark the content shareable.
7. WHEN the Founder rejects, THE OPS SHALL record the rejection reason and keep the content unshared.
8. THE OPS SHALL run the workflow through the ENGINE so that each step status and duration is stored.

### Requirement 40: Approvals for Sensitive Actions

**User Story:** As the Founder, I want to approve consequential actions, so that no agent acts externally without me.

#### Acceptance Criteria

1. THE OPS SHALL require an approved Approval_Request before performing any Sensitive_Action.
2. WHEN an agent proposes a Sensitive_Action, THE OPS SHALL create an Approval_Request that records the action type, target, exact content or parameters, requesting agent, and rationale, and SHALL hold the action pending.
3. THE API SHALL accept approve and reject decisions only from the Founder role.
4. THE OPS SHALL execute an approved action only with the exact content and parameters that were approved.
5. IF the content or parameters change after approval, THEN THE OPS SHALL invalidate the approval and require a new decision.
6. THE OPS SHALL record each decision with approver, timestamp, and reason in the Audit_Log.
7. IF an Approval_Request is not decided within a configured period, THEN THE OPS SHALL expire the request and SHALL NOT perform the action.
8. THE OPS SHALL record each external communication, once performed, in the Audit_Log with the approval reference.
9. IF an action of a Sensitive_Action type is attempted without an approved Approval_Request, THEN THE OPS SHALL block the action and write an Audit_Log entry.

### Requirement 41: Ops Dashboard

**User Story:** As the Founder, I want one place to see agent activity, so that I can supervise operations.

#### Acceptance Criteria

#### Acceptance Criteria

**User Story:** As the Founder, I want lead generation to be lawful and controlled, so that NEUROPATH avoids legal and reputational harm.

## Phase 6: Production Readiness

### Requirement 44: Security Hardening

**User Story:** As the Founder, I want a hardened platform, so that customer trust is protected.

#### Acceptance Criteria

1. THE Infrastructure SHALL encrypt all data in transit with TLS and all data at rest in S3, RDS, and queues.
2. THE Infrastructure SHALL keep S3 buckets private with public access blocked.
3. THE Infrastructure SHALL place the RDS database in private subnets with no public endpoint.
4. THE Infrastructure SHALL grant each compute role only the permissions it uses, and SHALL NOT use wildcard resource permissions for data access.
5. THE Platform SHALL keep sensitive data out of logs, and an automated test SHALL scan logs generated by the test suite for seeded sensitive values.
6. THE API SHALL set security headers including Content-Security-Policy, Strict-Transport-Security, X-Content-Type-Options, and frame protection.
7. THE API SHALL restrict cross-origin requests to configured origins.
8. THE Platform SHALL provide a completed security review recorded in `docs/SECURITY.md`, including prompt-injection and tool-permission test results.
9. THE Platform SHALL pass dependency vulnerability scanning with no unresolved critical findings.

### Requirement 45: Reliability, Monitoring, and Recovery

**User Story:** As the Founder, I want the platform to be observable and recoverable, so that outages are short and data is not lost.

#### Acceptance Criteria

1. THE Infrastructure SHALL enable automated RDS backups with a documented retention period, and SHALL purge deleted customer objects and their versions within the documented deletion window.
2. THE Platform SHALL document and test a restore procedure, and the restore test SHALL recover data to a verified state.
3. THE Platform SHALL emit structured logs, metrics, and alarms to CloudWatch for API errors, Job failures, queue depth, agent failures, and cost thresholds.
4. THE API SHALL expose a health endpoint that reports dependency status truthfully.
5. THE Platform SHALL define documented targets for recovery time and recovery point in `docs/DEPLOYMENT.md`.
6. THE Platform SHALL provide a documented deployment process with rollback steps.
7. THE Platform SHALL process dead-letter queue messages into alarms and visible admin records.

### Requirement 46: Test Coverage

**User Story:** As a developer, I want tests for each critical capability, so that no feature is claimed complete without evidence.

#### Acceptance Criteria
